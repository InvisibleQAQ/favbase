# lib/ingest

共享收藏收录 Module（docs/16 HIGH-1）：7 个平台 Adapter（github/bookmarks/x/zhihu/youtube/bilibili/douyin）共用唯一的 collection metadata 持久化实现。平台只声明归一化行 + 自己的 content chunker；schema 知识与不变量由本 Module 持有。Bilibili 的延迟转录不塞进 collection 模式，而是复用同一 Module 的 existing-item content operation。

## 模块结构

- `ingest.ts` — `ingestCollection(db, input) → IngestResult`。输入 `IngestInput`：`platform` + 归一化行数组 `sources`（`{platformSourceId, title, platformMeta?}`——meta 缺省 `{}`）/ `authors`（`{platformAuthorId, name, avatarUrl}`）/ `items`（`{platformItemId, platformAuthorId, title, authorName, originalUrl, publishedAt, contentState('pending'|'no_content'|'chunked'), platformMeta}`）/ `links`（`{platformItemId, platformSourceId}`）+ 可选 `content: { textOf(platformItemId), chunk(plainText) }`。输出：`inserted`（本轮新插入的 `{platformItemId, itemId}`）、`contentPersisted`（本轮实际写入 content+chunks 的 platformItemId——(新插入 ∪ 自愈幽灵) ∩ chunk 行落库成功，即 content-persisted seam）、`healedItemIds`（`contentPersisted` 中的自愈子集）、`droppedItemIds`、`droppedLinkItemIds`、`linkCount`。同文件还导出两个明确 operation：`settleItemContent(db,itemId,text,chunkText) → boolean`（docs/32 Step 5：写不透明文本正文**并落定** `content_state`——chunk 行写成才置 `'chunked'`，否则 `'no_content'`；**返回值 = chunk 行是否真的写入**，`true` 才许可调用方派发 Embed/Tag，chunker 产出 0 chunk 返回 false，保证自愈收敛；不发领域事件、不派发 lane，那是调用方的事。调用方：书签提取的 `saveBookmarkContent`，与 ghost sweep 里「本轮 `textOf` 给出文本」的分支。文本先经模块私有的 `storableText`（剔除 U+0000 再 trim，见下方不变量），再由两个**模块私有**函数处理（docs/33 Step 2.5）：`persistItemContent`（只做 `item_contents` upsert）+ `chunkAndSettle`（重建 chunk 行并落定状态，**不碰 `item_contents`**）；正文已在库里的条目——phase 5a 的新条目、从已存 `plainText` 治愈的幽灵——由 ingest 直接调 `chunkAndSettle`。写正文、写 chunk 与手写 `content_state` 的组合只能出现在本模块这一处，靠模块边界而不是守卫保证）；`persistExistingItemContent(db,platform,platformItemId,text,preparedChunks,subtitleSource) → 'chunked'|null` 供延迟内容 Adapter 使用，内部拥有 item lookup、`item_contents` upsert、prepared chunk replacement 与最终 `content_state='chunked'`。第 6 参 `subtitleSource: SubtitleSource | null` **必填、无默认值**（docs/29 Step 5）：转录正文传 `'official'`/`'asr'`，非转录内容显式传 `null`；可选参数会让漏传的调用方静默写 NULL，而 C6 本身就是一个被静默丢掉的来源；非空类型又会把这个通用 seam 锁死成只服务转录。今天唯一调用方是 B 站转录（`lib/bilibili/bili-sync-service.ts` 的 `persistContentChunks`）。正文 upsert 与回退到 `has_content` 在短事务内完成，chunk replacement 失败时错误向上抛且状态保持 `has_content`，禁止留下“新正文 + 旧向量”仍标 `embedded`；missing/blank/no-chunks 均零写入返回 null

测试 helper 不在本目录：`tests/ingest-test-support.ts` 的 `withChunkWritesCutShort(pg, fn)` 让 x / youtube / douyin 在各自同步入口复现「phase 5 中途断掉」（它们注入不了 chunker；`ingest.test.ts` 自己能注入，不用它）

## 幽灵消除（2026-07 修复，2026-10-04 补第二条，铁律）

- **`'chunked'` 只能由 chunk 行写入成功产生**：平台声明 `contentState:'chunked'` 的 item 在事务内以 `'has_content'` 中间态入库，phase 5（事务外）逐条写完 chunks 后才置 `'chunked'`；写入失败/中断停在 `'has_content'`。这条顺序由模块私有的 `chunkAndSettle` 持有，书签提取经 `saveBookmarkContent` → `settleItemContent` 走的是同一个函数（docs/32 Step 5 前两边各写一份）。修复前的顺序（事务内预宣告 chunked + 事务外慢写）在页面关闭/dev 重载时批量产出「chunked 零 chunk 行」幽灵——embed 批处理静默跳过、设置页重建被 `EXISTS` 过滤，全库零向量的根因
- **`'has_content'` ⇒ 正文已落盘**（docs/33 D6 / Step 2.5，用户 2026-10-04 决定修在共享管线里）：新条目的 `item_contents.plainText` 与 item 行**同一个事务**写入（step 4b）；声明 `'chunked'` 而正文为空的新条目直接以 `'no_content'` 入库，不经 `'has_content'` 中转。此前正文在事务外逐条写，phase 5 中途断掉时没轮到的条目停在 `'has_content'` 且没有正文，下一次 sweep 只认**那一次调用**的 `textOf`——抖音逐页入库、X 遇已知 id 即停、YouTube 对已入库视频不再拉详情，三者的 `textOf` 都覆盖不到上次留下的幽灵，于是永久落 `'no_content'`（insert-only，补不回来）。三个平台各有一条在自己同步入口复现的测试。调用不带 `content` 时没有正文可读，声明 `'chunked'` 仍以 `'has_content'` 入库（今天没有平台这样调）
- **同步自愈（ghost sweep）**：`content` 存在时 phase 5 兼扫平台幽灵（`contentState IN ('chunked','has_content')` 且零 chunk 行、非本轮新插入）。文本来源顺序：本轮 `textOf`（归一化后非空才算；经 `settleItemContent` 写入，可能与已存的不同）→ 已存 `item_contents.plainText`（`chunkAndSettle` 原样重切，不重写正文）→ 都没有则诚实回退 `'no_content'`——**最后一档只对上一条落地之前留下的幽灵可达**。治愈的 id 并入 `contentPersisted`/`healedItemIds`，顺现有链路进 embed/tag lane，无需一次性迁移。sweep 只在带 `content` 的调用里跑：一次运行可能一页都不入库的平台要自己保证每次运行至少调一次（抖音的 run 开头那次调用，docs/33 D-g）。github 侧配套 `getReposNeedingReadme`（幽灵仓库补拉 README，「无回填」ADR 的 bug 修复例外，见 `lib/github/CLAUDE.md`）。**bilibili 不受影响**：其同步不传 `content`，sweep 不运行（字幕 chunker 带时间戳，不能用 charSplit 重切）

## 管线持有的不变量

- **事务边界**：sources/authors/items/links 单事务 insert-only；`sources` upsert 是唯一例外（title/platformMeta/lastFetchedAt 刷新，重命名经此流入），items 为空也执行，好让平台报出的每个 Source 都刷新新鲜度。**「平台上次同步」已不再从这些行读**（docs/32 Step 1）：失败与空库早退的同步根本不写 source 行，这个问题移交给 Platform Sync Record（`platform_sync_records`，`lib/database/platform-sync-record.ts`）
- **Insert-only**（本文件即此规则的记录处；五个 sync-service、六个测试与四个 `lib/<platform>/CLAUDE.md` 曾引用一份从未进 git 的 ADR 文件，2026-09-30 已全部改指本文件，路径与来龙去脉见 docs/32 附录 B）：authors/items/item_sources `onConflictDoNothing`，first-write-wins；items/links 管线内按 first-seen 去重（items 按 platformItemId，links 按 (item, source) 对）。`platform_sync_records` 与 `sources` 同属状态行，**不适用**本规则，且不由本 Module 写（唯一写入方是 app 侧 Platform Sync funnel）
- **分批**：INSERT 走 `chunk(500)`（bind-param < PG 65535）；`item_contents` 行另用 `CONTENT_INSERT_CHUNK_SIZE = 20`——它受的是语句长度的限制：一条正文可达 100 KB（github `MAX_README_CHARS`），500 行就是一条 50 MB 的语句；知乎的 Markdown 没有长度上限，所以 20 限的是行数、不是字节数
- **id-map re-select 按 platform 全量**：覆盖本轮之前已存在的行——已知 item 新加入另一 source 仍会得到 link（youtube 全量重拉依赖此语义）
- **preExisting 差集**：content 对本轮新插入 item 写 + 幽灵自愈（见上方「幽灵消除」，健康的 preExisting 仍绝不重写）。集合由 `lib/database/collection-queries.ts` 的 `platformItemIds(tx, platform)` 在事务内读出（docs/32 Step 9；x / youtube / github / douyin 同步路径的已知 id 集合是同一个 builder）
- **两段式 content 写入**（docs/33 Step 2.5 起）：第一段在事务**内**——新条目的正文与 item 行一起落盘（step 4b，纯 insert：刚插入的行不可能已有正文行）；第二段在事务**外**逐条执行——`replaceItemChunks` 重建 chunk 行（它自开事务，单连接 proxy 嵌套死锁），写成后才置 `'chunked'`（chunker 产出 0 chunk → `'no_content'`）。**每个新条目的正文只写一次**：phase 5a 走 `chunkAndSettle`，不再 upsert `item_contents`（测试用 `BEFORE UPDATE ON item_contents` 触发器锁住，sweep 的已存正文分支同理）。**同事务的代价是失败范围变大**：`textOf` 现在在事务里被调用，它抛错整次入库回滚；step 4b 的正文 insert 失败也一样，回滚的是这一次调用的全部 source / author / item / link 行。embedding 不 inline（D3——管线保持零 storage/AI 依赖；同步后由 app 侧 Platform Sync funnel 派发共享 embed lane 排空平台积压，设置页「重建向量」为手动兜底）
- **正文入库前先归一化：剔除 U+0000，再 trim**（docs/33 Step 2.5 复核；主会话 2026-10-04 的默认决定，不是用户决策）：Postgres 的 `text` 存不了 U+0000（报 `invalid byte sequence for encoding "UTF8": 0x00`），而新条目的正文与 item 行同事务写，一条这样的正文曾让整次入库回滚、每次同步都如此——github README 最容易中招（`fetchReadme` 按 UTF-8 解码原始字节，UTF-16 的 README 解出来满是 U+0000）。模块私有的 `storableText` 是唯一的归一化函数，用在不透明文本经本模块进 `item_contents` 的每一处：step 3 里新条目的 `textOf` 结果、sweep 里本轮 `textOf` 的结果、`settleItemContent` 收到的文本（书签提取经此）。**归一化先于任何判空**：只剩 U+0000 的正文就是空正文——新条目直接以 `'no_content'` 入库；sweep 落到已存 `plainText` 分支，而不是把幽灵落成 `'no_content'`。chunker 只见得到归一化后的文本。原本存得进去的正文一个字符都不变。**两处已知缺口，没有处理**：① `persistExistingItemContent` 不归一化——chunk 是调用方备好的，只洗正文会让 chunk 行照样带着 U+0000，含 U+0000 的转录照旧在这里失败；② `title` / `platform_meta` 里的 U+0000 仍让入库事务整体失败（修复前也是：`title` 报同一个错，jsonb 报 `unsupported Unicode escape sequence`）。测试在 `ingest.test.ts`「Storable text」一组（四例）。源码里一律写转义 `'\u0000'`，不写字面 NUL 字符
- **`plain_text` 与 `subtitle_source` 总是一起写**（docs/29 Step 5）：三个写入方都显式写 `subtitleSource`——`persistExistingItemContent` 的 insert 与 `onConflictDoUpdate.set` 写调用方给的值；`persistItemContent`（经 `settleItemContent`：bookmarks 提取、sweep 的 `textOf` 分支）的 insert 与 `set` 写 `null`；`ingestCollection` step 4b 的事务内 insert 写 `null`（docs/33 Step 2.5 新增的第三个写入方，新行，无旧值可残留）。所以旧的 `'asr'`/`'official'` 活不过它所描述的正文。守卫在 `ingest.test.ts`：删掉任一 `set` 里的 `subtitleSource` 各红一例；`persistItemContent` 与 step 4b 的 insert `values` 里的 `null` 与列默认 NULL 等价，删它不红，是刻意为之的显式写法
- **Existing-item replacement**：以 `(platform, platformItemId)` 寻址；prepared chunks 允许 Bilibili 保留 start/end 时间戳；重转录覆盖 plain text、事务重建 chunks，并把 `embedded` 等旧状态回退到 durable `chunked` seam。该 operation 不启动 Embedding/Tagging/Processing Queue
- **Storage-free 加载图**：零 `@/lib/storage` 触达，`replaceItemChunks` 从 `@/lib/embedding/vector-store` leaf 导入（barrel 有 chrome.storage 模块加载副作用）；`ingest/ingest` 与七个平台 sync-service 一起由 `tests/lib-import-smoke.test.ts` 守卫（docs/20 高-1）

## 约定

- 平台差异留在调用方：入库前的去重/归一化（如 zhihu turndown、youtube 首见列表归属）、结果统计形状（各平台 `Sync*Result`）、空输入早退（bookmarks 空树零写入、zhihu 空收藏夹零写入）、author 过滤（x/youtube 剔除空 id）
- 消费方：7 个平台 Adapter 的 `sync*ToDb`；Bilibili folders/videos 也只传归一化 metadata，转录另走 existing-item operation；各自的 in-memory PGlite 守护测试验证等价性
- MEDIUM-2 已接线（以数据形式，管线自身零 tagging/embedding/storage 依赖）：content 步骤把实际持久化的 id（新插入 ∪ 自愈）收进 `contentPersisted`，各平台 sync-service 经 `Sync*Result.newItemIds` 透出，触发点是各 `entrypoints/app/sections/<platform>/<platform>-sync-adapter.ts` 经 `entrypoints/app/hooks/platform-sync.ts` 的 funnel（`runPlatformSync`，docs/32 Step 1；funnel 之外调 `startCollectionProcessingJobs` 由契约测试禁止）——tag lane 吃这批 ids（`tagNewItems`），embed lane 无视 ids、恒排空平台 `'chunked'` 积压（`embedPlatformBacklog`，见 `entrypoints/app/hooks/CLAUDE.md`）。x 已单一入口 app.html（07-20 删除 x.com 浮层按钮），旧「浮层 offscreen 路径不打标/不 embed」的欠账随之消失——恒打标恒 embed，见 `lib/x/CLAUDE.md`
