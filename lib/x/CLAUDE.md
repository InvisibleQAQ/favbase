# lib/x

X (Twitter) 书签收录领域（第四个平台，镜像 `lib/github/` 分层）。MVP = 从 X 私有 GraphQL 端点（用户登录态）一次性拉取全部书签 + PGlite 持久化 + 查询 + tweet 文本切块。复用现有表（sources/authors/items/item_sources/item_contents/item_chunks，`platform='x'` 判别列），零新表零迁移。X 无免费官方 API，故读 web 客户端书签页的 `Bookmarks` 内部操作——**防风控（anti-detection）是一等需求**。

**认证与请求构造照搬 supermemory 浏览器插件（`supermemory/apps/browser-extension`，2026-07 重写根因）**：此前 `chrome.cookies.get` 只读 `ct0`+`auth_token` 两个 cookie + 硬编码 bearer + 运行时解析 queryId + 发 `fieldToggles`，实测抓不到任何书签（X 端点对残缺 cookie 返回空/拒绝——SameSite=Lax 的 httpOnly cookie 跨源 fetch 从 jar 拿不到，手拼两 cookie 又不够）。现改为 supermemory 方案：background `webRequest.onBeforeSendHeaders` 拦截 x.com 真实请求，逐字捕获**完整 `Cookie` 串 + `x-csrf-token` + `authorization`**（session 存储）→ fetch 时原样回放（**不传 `credentials` 选项**——`credentials:'omit'` 会让 Chromium 丢弃显式 `Cookie` header，是 2026-07 rejected 根因，见下 fetch 约定）；请求侧**硬编码 queryId + 静态 features 映射、不发 fieldToggles、`count:100`+`includePromotedContent:false`**。**唯一保留 favbase 优于 supermemory 的部分**：`fetchPageWithBackoff` 的 HTTP-200-决不盲信错误暴露（见下），supermemory 会把 200-with-errors 静默吞成 `[]`（正是 07-16 "抓取为0" 的坑）。

**操作选型陷阱**：列全部书签必须用 `Bookmarks` 操作（响应包装 `data.bookmark_timeline_v2`）。`BookmarkSearchTimeline` 是书签**搜索**操作——`querySource` 是服务端校验枚举，不可用于 list-all。queryId `xLjCVTqYWz8CGSprLU349w`（取自 supermemory）硬编码；X 轮换 queryId 但 stale id 对该操作服务端长期保活，若 sync 抛 404/queryId 错误再从实时 x.com 书签请求刷新 `BOOKMARKS_QUERY_ID` + `TWITTER_API_FEATURES`。

## 模块结构

- `x-auth.ts` — **认证捕获层（照搬 supermemory `utils/twitter-auth.ts` + `storage.ts`）**：`captureXTokens(details)`（background webRequest 回调用）从 x.com 真实请求的 `requestHeaders` 逐字取 `authorization`/`cookie`/`x-csrf-token`，三者齐备才写 session 存储（`session:x-cookie`/`x-csrf`/`x-auth`，key 注册在 `lib/storage/keys.ts`）；模块级 `lastCapturedKey`（csrf + cookie 长度）去重避免每次 API 调用都写盘。`getXAuth(): XAuth|null`（`{cookie,csrf,auth}`，任一缺失返回 null）——**仅 storage-capable context 可调（扩展页 / background SW）；sync-service 自身零 storage 访问，auth 由调用方解析后传入**。**监听器注册在 `entrypoints/background.ts`**（`webRequest.onBeforeSendHeaders`，`urls:['*://x.com/*']`，`['requestHeaders','extraHeaders']`，observational 非 blocking 返回空）
- `x-api.ts` — X GraphQL「API」层（无 DB 导入、无 UI 文案，请求统一走 `fetchWithDeadline`——`lib/http/` 全平台共用 deadline），`getXAuth`/`XAuth` 从 `x-auth.ts` re-export：
  - 请求构造（照搬 supermemory）：`BOOKMARKS_QUERY_ID='xLjCVTqYWz8CGSprLU349w'` 硬编码 + `TWITTER_API_FEATURES` 静态 features 映射（verbatim 自 supermemory）+ **不发 fieldToggles**。`buildHeaders(auth)` 原样回放捕获的 `Cookie`/`x-csrf-token`/`authorization`（+ content-type/Accept）
  - `fetchAllBookmarks(auth, onProgress?, { shouldStop? })` — 串行游标分页。variables `{count:100, includePromotedContent:false}` + 第 2 页起 cursor。响应路径 `data.bookmark_timeline_v2.timeline.instructions[]`（防御性兼容 `bookmark_collection_timeline` 包装）；bottom cursor = `content.cursorType==='Bottom'` 的 entry。停止条件：entries 空 / bottom cursor 不变 / `shouldStop(id)` 命中已存 id（增量）。fetch 用 `credentials:'omit'`（只靠显式 header，避免 jar cookie 冲突/SameSite 丢失）
  - 纯函数导出供单测：`parseTweets`、`extractBottomCursor`、`mapTweetToRow`（含 `TweetWithVisibilityResults` 拆包 + photo/best-mp4 media 提取 + url 派生）、`buildBookmarksUrl(opts?)`（发送静态 features、无 fieldToggles）。原始行类型 `XRawBookmark`
  - 结构化错误：401/403 → `XAuthError`（带 `reason: 'no-token'|'rejected'`——`no-token`=会话未捕获（调用方 auth 为 null 时由 sync-service 抛/bg 直接合成），`rejected`=X 拒绝回放（401/403），两者用户动作不同：刷新页面 vs 重新登录）；429 或 body `errors[].code===88` 重试耗尽 → `XRateLimitError(resetAt)`；其余非 2xx → `Error` 附响应 body 前 300 字符（X 错误 body 含精确诊断，如缺失 feature 清单）
  - **HTTP 200 决不盲信（防"抓取数为0 静默成功"，favbase 独有、supermemory 无）**：X 把服务端拒绝当 200 返回。`fetchPageWithBackoff(url, headers)`（导出供 fetch-mock 单测）读一次 body 后，除 `code:88`（保持 XRateLimitError 重试）外：① body 含非空 `errors[]` 且有任一 `code≠88` → 抛 `Error`（含各条 `code N: message` + body 前 300 字符）；② body 既无 `errors` 也无 `data.bookmark_timeline_v2`（未知形状，如 queryId/features 腐烂）→ 抛 `Error("unexpected X response shape …")`。**但 200 带 `bookmark_timeline_v2` + 空 instructions 是合法的"零书签"结果 → 返回不抛**（`hasTimelineShape` 判定）。所有此类抛错消息尾附 `[queryId=xLjCVTqYWz8CGSprLU349w]` 诊断——一次实测抛错即可定位是否 queryId/features 需刷新。此前 `chrome.cookies` 两 cookie 方案静默吞成"0 抓取, 成功"，是 07-16 的根因
- tweet 切块用共享 `charSplit(text, { preferParagraph: false })`（`lib/embedding/char-split.ts`，docs/16 MEDIUM-4——原 `x-chunker.ts` 已删并入）：普通推文 1 chunk；长 premium（note）推文按 `MAX_CHARS=1500` 软切，`preferParagraph:false` 仅优先句末标点（`。.!?！？;；…\n`）回看 300，无句断则硬切。无时间戳（图文内容 → NULL start/end 列）
- `x-sync-service.ts` — **DB schema 知识的唯一持有者**（`PLATFORM='x'`）。同步：`syncBookmarks(auth, onProgress?)`（auth 由**调用方**在能读 storage 的 context 里 `getXAuth()` 解析传入，null 抛 XAuthError → 读已存 id 建增量 `shouldStop` → fetchAllBookmarks → `syncBookmarksToDb`；本函数自身零 storage 访问——lib 层 sync-service 的加载图必须 storage-free，由 `tests/lib-import-smoke.test.ts` 守卫（docs/20 高-1）；`ingestCollection` 同样 leaf 导入 vector-store、零 `@/lib/storage` 触达，见 `lib/ingest/CLAUDE.md`；同 `x-auth.ts` 只 import `@/lib/storage/keys` 的理由）、`syncBookmarksToDb(db, bookmarks)`（导出供测试：批内 byId 去重后，事务骨架委托 `ingestCollection`（docs/16 HIGH-1）——本函数只声明归一化行：单 source `'bookmarks'`、authors 剔除空 restId、content=`{textOf: tweet text, chunk: charSplit(·, {preferParagraph:false})}`）。`SyncBookmarksResult.newItemIds`（= 管线 `contentPersisted`）是自动打标 + 自动 embed 输入——**触发点在 app.html 调用方 `use-x-bookmarks.ts` syncFn，本文件禁止 import `@/lib/tagging` 和 `@/lib/embedding` barrel**（config→storage 链在模块加载期触碰 `chrome.runtime`，`tests/lib-import-smoke.test.ts` 会红；char-split / vector-store leaf 导入不受限）。查询（X 收藏页数据来源，UI 零 drizzle 导入）：`getBookmarks({author?, search?, page, pageSize})`（`publishedAt DESC NULLS LAST`；author 精确匹配 handle chip；search 对 title/text/authorName ILIKE，转义 `%_\`）、`getAuthorCounts()`（按作者分组降序，chip 行）、`getLastSyncedAt()`。UI 行类型 `XBookmarkItem` 在此导出。守护测试 `x-sync-service.test.ts`（in-memory PGlite）
- `x-messages.ts` — X 同步的结构化错误分类（纯类型 + 分类器，无 wire 消息）。`classifyXSyncError(err) → XSyncError`（`auth`/`rate-limit`+resetAt/`unknown`，从 app.html hook 下沉到此；i18n seam 仍在 UI 边界）。**曾有的浮层 wire 消息（`X_SYNC_START`/`X_SYNC_PUSH`）+ offscreen `OFFSCREEN_X_SYNC*` + `lib/offscreen/x-sync.ts` runner + `lib/background/x-handlers.ts` 中转已随 x.com 浮层按钮整体删除**（07-20：浮层冗余，app.html 已能自同步）

## 单一触发点

`syncBookmarks(auth, onProgress?, control?)` 自身上下文无关（`getDb()` 在扩展页=RPC proxy；零 storage 访问）。`fetchPageWithBackoff` 在每次请求/重试前执行 cooperative checkpoint，当前 fetch 不取消。唯一驱动仍是 app.html `/collections/x` 手动按钮；返回后 hook 将 `newItemIds` enqueue 到共享 `x-bookmarks:embed|tag` lanes。x.com 浮层触发点保持删除，auth 捕获链完整保留。

## 约定

- **共享骨架**：写侧走 `ingestCollection`（`lib/ingest/`，docs/16 HIGH-1——事务边界/insert-only/分批/id-map/两段式 content 均由管线持有）；读侧 `escapeLike` 自 `lib/database/sql-utils.ts`，`getBookmarks` 走 `pagedItemsQuery`、`getLastSyncedAt` 走 `getPlatformLastSyncedAt`（`lib/database/collection-queries.ts`）——本文件只留平台特有 filter/orderBy/mapRow，勿再拷贝
- **Insert-only（与 B站/github/bookmarks 同 ADR）**：items/authors/item_sources 只 insert（`onConflictDoNothing`，first-write-wins），不 update 不 delete。重新同步只追加新书签；metadata 不刷新；取消书签不删行。唯一例外：`sources` 单行（`platformSourceId='bookmarks'`）upsert 刷新 `lastFetchedAt`。完整 ADR 见 `.trellis/spec/frontend/database-bridge.md`
- **content_state='chunked' + 延迟 embed（D3）**：tweet `full_text` 即内容，同步时写 `item_contents` + `charSplit(preferParagraph:false)` 切块 → chunk 行写成后才置 `'chunked'`（事务内中间态 `'has_content'`，见 `lib/ingest/CLAUDE.md` 幽灵消除；游标覆盖不到的老幽灵在 sweep 中回退 `no_content`），**但不 inline embed**（数千书签会打爆 embedding provider）。向量化由同步收尾派发的 embed lane 排空平台积压（`embedPlatformBacklog`），设置页「重建向量」为手动兜底。同步后全文（ILIKE on title/text）即可搜
- **items 行映射**（PRD Technical Notes）：`platformItemId=rest_id`、`title=full_text` 截断 140 字符（空回退 handle）、`authorName=用户显示名`、`authorId → platform_author_id=用户 rest_id`、`originalUrl=https://x.com/{handle}/status/{rest_id}`、`publishedAt=created_at`
- **platformMeta 形状**（items，写入方即本目录）：`{ text, authorHandle, authorName, avatarUrl, media[], likeCount, retweetCount, replyCount, lang }`（camelCase）。media 项 `{ type, url }`。防御式收窄由本目录导出的 `narrowXMeta(meta, { title, authorName })` 单点持有（内含 `narrowMedia` 逐项校验 `{type,url}`），sync-service `mapRow` 与 section `tagged-tweet-card` 共用
- **`narrowXMeta` 导出**（sync-service）：`narrowXMeta(meta: unknown, fb: { title, authorName }): NarrowedXMeta`（= `Omit<XBookmarkItem, envelope>`）。text 缺失回退 `fb.title`、authorName 回退 `fb.authorName`（均**空串保留**、仅非 string 回退）。envelope（id/tweetId/title/originalUrl/publishedAt）留各调用点
- **防风控常量**（`x-api.ts`）：`PAGE_SIZE=100`（照 supermemory，更少请求=更快全量）、页间 `BASE_DELAY_MS=1000 + Math.random()*JITTER_MS(500)` 抖动、串行无并发、`x-rate-limit-remaining<=REMAINING_STOP_THRESHOLD(3)` 主动暂停至 `x-rate-limit-reset`、429/code:88 → sleep 至 reset 后**重试同页**、5xx 瞬态 `MAX_RETRIES=5` 上限指数退避、增量 stop-on-known-id 封顶 re-sync 成本。数值全部经 `envNumber('VITE_X_*', default)` 可配置（`lib/env.ts`，注释文档在 `.env.example`）；sleep/抖动/指数退避机制共享自 `lib/http/backoff.ts`，勿再复制实现
- **fetch 构造照搬 supermemory（无 DNR、无 `credentials`）**：`fetch(url, { method:'GET', headers, redirect:'follow' })`——**决不传 `credentials:'omit'`**：omit 语义是"本请求排除 credentials（cookie）"，Chromium 据此把我们显式设的 `Cookie` header 整个丢弃，X 收到无 cookie 请求 → 401/403（2026-07 rejected 根因，供成功案例 supermemory 对照发现）。host-permitted 的扩展上下文 fetch 被当 same-site（浏览器不加 `Origin`），且 Chromium 不会把 `chrome-extension://` referrer 发给 web origin——与 supermemory 可用请求的画像一致，故**已删除 DNR rule id:2**（旧 Origin/Referer 改写在无 credentials:'omit' 时纯属多余）。`x-client-transaction-id` 仍省略——靠 pacing+backoff+增量兜底
- 权限：`*://x.com/*` 静态 `host_permissions` + `webRequest` perm（捕获认证 header）。`cookies` perm 仍在但 x 已不用（bilibili 用）；已移除 `abs.twimg.com`（旧 queryId resolver 用，已删）。**无 Connections 卡（D6）**：登录态在同步时才校验——但认证已从"静默读 cookie"改为 **webRequest 捕获**，故 UI 空态引导「打开 x.com/i/bookmarks 登录，让扩展捕获会话后回到此处点同步」（deep-link，`x.notLoggedInDesc`——登录后页面自身的 Bookmarks 请求即触发捕获），用户须本 session 访问过 x.com 才能捕获到 token。缺失/过期 → `XAuthError` → 该空态。无 `UserSettings.xToken`、无 `configSavedAt.x`
- 运行位置：app.html 页面 context，经 RPC proxy 写 Offscreen PGlite（与其他平台同步一致）
- 未覆盖（Out of Scope，见 PRD）：Premium「书签文件夹」API（扁平单集合）、写/删书签（只读收录）、`x-client-transaction-id` 生成、inline embedding、tweet 媒体下载/thread 展开、多账号
