# app/hooks

app.html 专用共享 hooks（跨 section 复用；平台无关）。与 `lib/hooks/`（跨 context 共享，如 useSettings）区分：本目录的 hook 只跑在 Extension Page context。

## 模块结构

- `background-jobs-store.ts` — 模块级 `useSyncExternalStore` job store **兼 Pipeline Run scheduler**（audit 2026-08-17 #7 收敛产物），跨 Hash Router 挂载保留 `sync|extract|embed|tag|transcribe` 未完成态。`startJob(platform, kind, runner, collision='drop')` 的碰撞语义是**显式策略**：`'drop'`（active 时拒绝，`started:false`——sync/extract 跨挂载去重）、`'queue'`（FIFO 入 pending，active settle 成功**或失败**后由 store 同步出队接续）、`'coalesce'`（并入最新的**同为 coalesce 派发**的 pending run，本次 runner 丢弃；绝不并入 `'queue'` 条目——可互换性由派发方声明，如全量 backlog embed drain 互吸、但不吸 streaming drain）。句柄 `{started, dispatch:'started'|'queued'|'coalesced'|'dropped', settled}`，settled 结算于**本次派发对应的 run**。调用方禁止再用 settled-promise 重试循环自造排队。owner token 保证旧 run 迟到 settlement/progress 不覆盖新 run；`trackJobRun` 仅为不可控旧 Promise 的兼容 observer（group settle 后同样 drain pending——`bilibili:transcribe` key 上 observer 与 owner 混用），不得用于需要暂停的 pipeline。**闸门经 `setJobGate(reader)` 依赖注入**（本模块属泛型层，禁止直接 import `library-gate`），且在 run **实际启动时**评估（含 pending 出队时刻）：命中时 job 照常创建、runner 照常启动，只是 control born-paused、初始 phase `'paused'`，`started` 仍为 `true`——**绝不能返回 `{started:false}`**，否则排队中的工作被结算成空。仅注册 reader 不触碰已运行 run（暂停靠 `library-gate` 的 `pauseJob` fan-out）。reader 抛错被吞（记 `console.error`）并按未暂停处理。
- `pipeline-run-control.ts` — 单 run cooperative pause 状态机；Pause 先进入 `pausing`，worker 在下一个 `checkpoint()` 才进入 `paused`，Resume 从 `pausing|paused` 都回到 `running`：前者撤销尚未生效的暂停意图，后者释放等待，禁止丢失 checkpoint 前到达的 resume。不取消当前请求或 DB 写入。**`createPipelineRunControl(onPhaseChange, initialPhase='running')` 支持 born-paused**（闸门用）：初始 `'paused'` 的 run 在**第一个** `checkpoint()` 就挂起，因此 checkpoint 守卫是 `if (phase === 'running') return`；resume 若早于首个 checkpoint，checkpoint 直接放行、不产生第二个 worker。
- `collection-processing-jobs.ts` — 六平台 Embed/Tags 的 app-runtime 执行器。每个 `(jobPlatform,lane)` 各自串行、各自可暂停，不同平台 Embed lane 可并行；item 在领取前 checkpoint。碰撞排队**全部由 job store 的策略执行**，本模块只声明：tag batch = `'queue'`（每批 ids 不同，逐批必跑）、embed batch = `'coalesce'`（runner 都是全量 `'chunked'` backlog drain，可互换，N 个碰撞收敛为 1 个 pending drain）、streaming drain = `'queue'`（排在同 lane batch run 之后）；均不丢工作，模块内无 settled 重试递归。streaming item 进入模块级 inbox（item 队列 + done/total 是 lane 的 item 级簿记，留在本模块），drain settle 后若 inbox 有迟到 item 则 re-wake。同步收尾时 Embed 恒派发平台 `'chunked'` backlog，Tags 仍只吃本轮 ids；provider 保存恢复则只派发对应平台 Embed/Tags backlog。诊断：`scheduler:batch-queued`/`batch-coalesced`/`stream-queued` 取代旧 collision/retry 事件；终态 `job:completed|failed` trace 在 runner wrapper 内发出（queued run 的 settled 解析时 store 可能已启动下一个 run，读快照会串台）。队列仅存活于当前 app.html，不伪装持久恢复。
- `collection-job-platform.ts` — 纯平台判别符 ↔ background-job namespace 映射；exhaustive `Record<CollectionPlatform,string>` 是需要通用正反翻译时的唯一事实源，供 `library-gate`、provider 恢复门面、funnel，以及 `sections/**` 每一处 job 命名空间（`startJob`/`useJob` 第一参、`jobPlatform:`，docs/32 Step 5 起契约测试禁止手写字面量）共同消费。禁止在这里读 storage 或注册 job gate，避免纯翻译触发 app-runtime 副作用。
- `collection-processing-resume.ts` — provider 保存后的平台感知恢复门面：`resumeCollectionProcessing(platform,'embedding'|'llm')` 经纯 mapping Module 派发一个 Embed/Tags backlog run。Settings 不接触 job key、查询或 lane collision；active lane 的后续跑仍由 `startBatchLane` 保证。
- `use-collection-library.ts` — 单列表 + facet + 手动同步的共享状态机；同步经 `startJob(jobPlatform,'sync')`——config 键 **`jobPlatform` 就是 background-job 命名空间**（`useJob(jobPlatform,'sync'|'embed'|'tag')` 也用它，兼作 `console.error` 前缀），调用方必须传 `jobPlatformForCollection(platform)`（docs/32 Step 5：github/x/zhihu/youtube 的 `jobPlatform` ≠ 平台 id，抄字面量会让手动同步与 funnel 派发的 embed/tag lane 落在两个命名空间；键名原叫 `logTag`，docs/32 Step 7 改名），把 cooperative checkpoint 传给平台 `syncFn`，并暴露同 namespace 的 typed `syncJob`/`embedJob`/`tagJob` 给 pipeline Adapter。**返回的通用字段（`items`/`filter`/`setFilter`/`facets`…）由 view 直接消费**：docs/32 Step 7 删掉了五个平台 hook 的改名层与 `Use*Return` 接口，平台 hook 只注入稳定函数并叠加自己的触发策略 / 平台特有状态。平台只注入稳定的 query/facets/lastSynced/sync Interface；**不再注入 error classifier**（docs/32 Step 4 删掉了 `classifyError` 与 `TError` 泛型，4 → 3 个类型参数）：`syncError: CollectionSyncError | null` 由本 hook 调唯一的 `classifyCollectionSyncError` 算出——五个调用方注入的本来就会是同一个函数。`controlledFilter?: string | null` 是唯一的受控 seam（docs/20 中-6）：`undefined` = 非受控（`setFilter` 拥有 filter，五个远程平台现状）；给值（`null` = 无筛选）即外部事实源（如路由参数）拥有——hook 读它、变化时在 **render 期**把 page 回 1（非 effect，避免一次「新 filter + 旧 page」废查询）、`setFilter` 变 no-op，杜绝两个事实源。**触发时机（按钮/挂载/daily）是 adapter 的策略，hook 不带 auto-on-mount 开关**。导出 `SEARCH_DEBOUNCE_MS = 300`（docs/32 Step 6）——app.html 收藏页搜索防抖的唯一定义，另两个消费方 `sections/bilibili/bilibili-view.tsx` 与 `sections/collections/use-collections.ts` import 它（Content Script 字幕面板的 100 是另一个入口另一个值，不归这里）。单测 `use-collection-library.test.tsx`（受控/非受控 filter 归属与回页）。
- `facet-query.ts` — `facetQuery(query, facetKey)`（docs/32 Step 7，泛型层纯函数，单测 `facet-query.test.ts`）：单维 facet 平台共用的 `queryFn` 规整——把 hook 的 `filter` 写进平台查询自己的 facet 键，`null` filter / `''` search 变成省略字段，`page`/`pageSize` 原样。五个平台 hook 各在模块级写一行 `const queryFn = facetQuery(get<P>…, '<key>')`（模块级 = 引用稳定）。`TQuery`/`TItem` 由平台查询函数推出、调用点零断言；facet 键类型是 `Exclude<keyof TQuery, 'search'|'page'|'pageSize'>`，拼错（`'lang'`）或填 `'search'` 是 `tsc` 错误（落地时用临时探针文件实证过）。函数体唯一的 `as TQuery` 不能删：去掉它 `tsc` 报 TS2345——对象字面量满足约束，但 `TQuery` 可能被实例化成约束的另一个子类型（同样实测过）。只 `import type` 自 `./use-collection-library`。
- `use-credential-gated-library.ts` — `useCredentialGatedLibrary(credentials, config)`（docs/32 Step 7，**平台感知层**：经 `useSettings` 读 storage，单测 `use-credential-gated-library.test.tsx`）：`'credentials'` 平台（github、youtube）的页面门。`credentials` 是平台 adapter 导出的唯一解析函数（`githubCredentials` / `youtubeCredentials`，返回凭据或 `null`），与 adapter 的 run 门、`probeReady` 是同一个函数，三处不会再分叉。返回 `useCollectionLibrary(config)` 的全部字段 + `configured`（`credentials(settings) !== null`）+ `settingsLoading`，并把 `sync` 换成「未配置时静默 no-op（不 `startJob`、`syncing` 不翻转）」的版本——与两个平台改前的门逐行等价；settings 加载期间是 `DEFAULT_SETTINGS`（无凭据），所以这段时间的 `sync()` 同样静默。门是 `useCollectionLibrary` 之外的独立 hook：泛型层零 storage（spec §7.2）。不 import `sections/`。
- `collection-sync-error.ts` — 同步 / 浏览错误的唯一分类器（docs/32 Step 4，泛型层，单测 `collection-sync-error.test.ts` 用六平台**真实**错误类）：`CollectionSyncError = auth{reason,message} | rate-limit{resetAt,message} | unknown{message}`，`classifyCollectionSyncError(err)` 只看 `lib/collections/sync-errors.ts` 的两个基类、不认识任何平台（每个变体都带原始英文 `message`：bookmarks 没有凭据也没有限流，view 直接显示它，零新键）；`rateLimitRemainingMs(error, now)` 纯函数，给按钮锁用。**刻意零 i18n**：`useCollectionLibrary` 与 B 站两个 hook import 它，而 `@/lib/i18n` 在加载时就读 `chrome.storage`——无 chrome 的测试里会冒出 unhandled rejection（2026-09-30 实测：`@wxt-dev/storage` `getStorageArea` 读 `undefined.runtime`），`use-collection-library.test.tsx` / `use-bookmarks.test.tsx` / `use-bili-fav-folders.test.tsx` 都没 mock i18n。
- `collection-sync-error-message.ts` — 上面那个分类结果的 i18n seam（只有 view import）：`SyncErrorCopy { auth, authRejected?, rateLimited, rateLimitedUntil? }`（全是 `LocaleKeys`）+ `syncErrorMessage(error, copy)`——auth 在 `rejected` 且给了 `authRejected` 时用它，否则 `auth`；rate-limit 有 `resetAt` 且给了 `rateLimitedUntil` 时插值 `{{reset}}`（`formatDateTime`），否则 `rateLimited`；unknown 原样返回 message。可选键缺省 = 平台不认识这个维度（只有 X 分两种 auth，只有 github/x 拿得到 reset），不是隐藏特例。view 以模块级常量声明一份 `SYNC_ERROR_COPY`，**不再写 switch**。与分类器分两个文件纯粹是为了上一条的 i18n 加载副作用。
- `use-countdown.ts` — 全 app 唯一的 1 s 倒计时（docs/32 Step 4，单测 `use-countdown.test.ts`，含从 `sections/x/cooldown.test.ts` 搬来的 `formatCountdown` 用例）：`useCountdown(remainingAt: (now) => number): number`，只在剩余 > 0 时挂 1 s interval、归零即清；`formatCountdown(ms)`（从 `sections/x/cooldown.ts` 搬来，实现不变）。**`now` 在渲染期读 `Date.now()`，不存 state**——页面挂了很久才出现的 deadline（挂载 10 分钟后才到的限流错误）首帧必须按此刻算；存在 state 里的 `now` 在没有倒计时时不 tick，会停在挂载时刻，首帧就多算 10 分钟（回归例锁住，换回旧写法实测红 `expected 605000 to be 5000`）。interval 只负责触发重渲染；`remainingAt` 每次渲染都是新闭包，故不进 effect 依赖（依赖只有 `active`）。消费者：X 冷却（`use-x-bookmarks.ts`）与 github / x 两个 view 的限流按钮锁（`rateLimitRemainingMs`）。
- `collection-phase.ts` — `resolveCollectionPhase(state): CollectionPhase`（audit docs/15 HIGH-2 的收敛产物）：收藏页内容区的 8 分支优先级阶梯纯函数。返回 discriminated union `'tag-filtered' | 'query-error' | 'auth-failed' | 'sync-error' | 'skeleton' | 'empty-library' | 'no-matches' | 'grid'`。**分支顺序即契约**——顺序封在这一处，各 view 只做 `switch(phase)` → 平台节点映射，view 不再各自维持顺序（消除「某平台漏 authFailed 短路」类静默 bug）。入参是布尔旗标对象（tagFiltered/queryError/authFailed/syncErrorEmpty/metaLoading/syncingEmpty/libraryEmpty/loading/noMatches）；无 authFailed 概念的平台（github：token 缺失走 view 的配置门整页短路）传 `authFailed:false`。`collection-phase.test.ts` 逐分支 + 全旗标叠加锁死顺序
- `use-processing-coverage.ts` — 平台级 DB Processing Coverage hook：返回 `loading|ready|error` 判别状态，订阅 durable content/embedding/tagging 事件，并以 100ms trailing window 合并聚合查询；无轮询。
- `pipeline-segments.ts` — 纯 Adapter Module：平台声明 stage→coverage key 与可选 runtime；`backgroundJobRuntime(job, progressAdapter?)` 输出**纯展示** runtime 快照（phase/progress/lastProgress/error，无 pause/resume——段级控件已下线，运行控制归 per-platform 闸门 `library-gate.ts` + `components/library-gate/`），`completedProgress:'last-run'` 只给 Fetch 保留本次总数并显示 100%。Module 统一 live-over-idle、unknown、loading/error 与 job payload 校验。**收藏页 pipeline 形状的唯一声明点 `collectionPipelineStages({ labels, fetch, content?, embedJob, tagJob })`**（docs/20 中-7，2026-08-22）：Fetch（`acquisition`，`completedProgress:'last-run'`）→ 可选 content 段（github readme / bookmarks extraction / bilibili transcription；x/zhihu/youtube 无）→ Embedding → Tagging，embed/tag 恒走默认 runtime adapter；`fetchedCountProgress` 是「同步进度带 `fetchedCount`、远端总数未知」平台共用的 Fetch adapter（github/x/zhihu/youtube/bilibili；bookmarks 用默认 `readJobProgress`）。view 不得再手写 stages 数组。
- `use-collection-pipeline.ts` — 收藏页 pipeline 编排 hook（泛型层，docs/20 中-7，单测 `use-collection-pipeline.test.tsx`）：`useCollectionPipeline({ platform, syncing, fetch, content?, embedJob, tagJob, extraRefreshKey? })` → `{ coverage, coverageStatus, segments }`。内部拥有三件事：(1) `useProcessingCoverage` 的 refresh key——纯函数 `collectionCoverageRefreshKey` = `${syncing}:${embed gen}:${tag gen}[:extra]`；`syncing` 独立于 `fetch.running`，因为 github 在 readme 相位把 Fetch 段提前 settle 而 sync job 仍在跑；`extraRefreshKey` 承接平台附加的非 job 信号（bookmarks `extraction.running`，bilibili `autoTranscribe.running`/`activeBvid`/`transcribeJob.generation`）；(2) `pipeline.fetch/embedding/tagging` 三个共享标签的翻译（`useTranslation` 订阅，同 `use-jobs-badge` 先例；content 段 label 由 view 翻译后传入）；(3) `collectionPipelineStages` + `buildPipelineSegments`。六个 view（含 bilibili 的 folder 页与 fallback 页）全部消费它，view 只注入 Fetch runtime（`backgroundJobRuntime(syncJob, fetchedCountProgress)` 或默认）与 content 段，再 `<PipelineProgressStrip segments={segments} />`；github 的 readme settled 特例留在 view。`CollectionConfigurationNotice` 吃它返回的 `coverage/coverageStatus`。
- `use-collection-breadcrumbs.ts` — 收藏路由祖先路径（docs/25 Step 8，单测 `use-collection-breadcrumbs.test.tsx`）：`useCollectionBreadcrumbs(platform | null, leaf?)` → `BreadcrumbsLinkProps[]`。`null` = 聚合页 `/collections`（`首页 / 收藏夹`），平台 = `首页 / 收藏夹 / 平台名`，带 `leaf` 再多一级（bilibili 的收藏夹名）。**末项永远无 href**（`BreadcrumbsLink` 渲染成 `aria-current="page"` 的惰性项），实现上是「先排祖先、再摘掉最后一格的 href」，没有 per-case 分支。crumb 文案与 path 唯一来源是 `collection-platform-registry.ts`（`collectionPlatformById`）+ `nav.collections` + `breadcrumbs.home`，因此末项取的是**导航名**，可能与页面 h1 不逐字相同。**不 memo**：`t` 是稳定的模块函数，`useMemo` 会把字符串冻在旧 locale；重算成本是三个数组元素。属泛型层（零 storage、零 `sections/` import），`collection-platform-registry.ts` 在 app 根不在 `sections/`。
- `daily-sync-gate.ts` — 每日自动同步闸门纯函数（无 React/storage，单测 `daily-sync-gate.test.ts`）：`isSameLocalDay(a,b)`（本地年月日三相等）、`shouldAutoSync(lastAttemptAt, now)`（`null`→true，否则「非今天」→true）。**输入 = Platform Sync Record 的 `last_attempt_at`**（docs/32 D2，2026-09-30 落地）：当天只要有过一次尝试——手动或自动、成功/失败/静默/未结束——当天的自动名额就用掉了；手动按钮不受限。推翻了 07-26 的「复用 `sources.lastFetchedAt`、不建表」（失败与空库同步不写 source 行，旧闸门把它们读成「从未同步」，每次切回标签页都重打刚风控过我们的平台，docs/32 高-1）。判定逻辑与本地自然日边界没改，只换了入参。
- `platform-sync.ts` — **Platform Sync funnel**（docs/32 Step 1，**平台感知层**：认识 `CollectionPlatform` 与 `jobPlatformForCollection`，与 `library-gate` / `use-daily-auto-sync` 同档；泛型层不得 import 它；它不 import `sections/`）。`runPlatformSync(platform, control, sync, deps?)` 是 Platform Sync **被记录**与**派发处理 lane** 的唯一位置，六个 `*-sync-adapter.ts` 在各自函数体**内部**调用它、包住联系平台的那段（不包 adapter 本身——`run<P>Sync` 对外签名不变，`collection-platform-auto-sync.test.ts` 的 `toBe` 身份锁定照绿）。顺序写死：`control.checkpoint()`（born-paused 的手动 run 恢复前不记尝试）→ `recordAttempt` → `sync()` → 失败：`recordFailure`（自身出错只 `console.error`，**rethrow 原错误**）→ 成功：先 `dispatch`（= `startCollectionProcessingJobs`，`jobPlatform` 派生）再 `recordSuccess`（它抛则 job 失败、记录停在 NULL 仍占当天名额，lane 已派发）。导出 `PlatformSyncOutcome { fetched, inserted, newItemIds }`（bilibili/bookmarks 逐条处理，传 `[]`）与 `PlatformSyncDeps`；默认 deps 用 `await initDbProxy()` 取 db（幂等，堵住 app 启动 fire-and-forget init 尚未 settle 的窗口）绑 `lib/database/platform-sync-record.ts` 的三个写函数。**不做策略**：不认识静默错误、闸门、冷却（architecture-audit:296）。**凭据缺失在 funnel 之前判定**不是它的职责而是 adapter 的：不联网就能知道的缺失（github/youtube 空转 return、x/bilibili 抛原错误类）不算尝试、不写记录（docs/32 §5.2）。单测 `platform-sync.test.ts`；funnel 之外调 `startCollectionProcessingJobs` 由 `tests/platform-completeness-contract.test.ts` 按 AST 禁止
- `library-gate.ts` — per-platform「知识库构建」持久闸门门面（**平台感知层**，与 `use-daily-auto-sync.ts` 同档：读 storage + 认识平台词汇；泛型层不得 import 它）。持久值 = `libraryGateStorage`（`local:library-gate`）里**暂停中的平台列表**，`[]` = 全部运行（第 7 个平台接入零改动）。模块级 `Set<CollectionPlatform>` 同步镜像供非 React 的 `startJob` 当 tick 判定，模块加载时 `getValue()` 填充 + `.watch()` 订阅跨 context 变更（形态同 `lib/i18n/index.ts` 的 `currentMessages`）。导出 `isLibraryPaused(jobPlatform)` / `gatePlatformOf(jobPlatform)` / `pauseLibrary` / `resumeLibrary` / `useLibraryGate(platform)`；正反 namespace 翻译委托给无副作用的 `collection-job-platform.ts`。`pause/resumeLibrary` 先改镜像（同 tick 生效，防点击与派发竞态）→ 再写 storage（watch 回声因值相同被吞）。**运行中 run 的 `pauseJob`/`resumeJob` 联动（5 个 kind fan-out）在 `applyPaused` 内按新旧集合 diff 驱动**——点击路径与跨 context watch（另一个 app.html tab 的写入）共用同一处联动逻辑；pause/resume 相位守卫使无 run 时（如模块加载的初始读）为幂等 no-op。**模块加载时 `setJobGate(isLibraryPaused)` 自注册**，app.html 的加载保证来自 `use-daily-auto-sync` 的 import（它由 `App.tsx` 挂载）。
- `use-jobs-badge.ts` — 工具栏 badge 同步 hook（挂 DashboardLayout，泛型层；单测 `use-jobs-badge.test.ts`）：`useRunningJobs().length` → `browser.action.setBadgeText`（数字，0 清空）+ `setTitle`（复用 `backgroundJobs.reminder` 文案当悬停提示，locale 切换随 re-render 更新）+ warning 橙底色。**只写不清理**：badge 文本是浏览器会话级持久，关掉 app.html 后由 SW 清道夫兜底擦除（`lib/background/jobs-badge.ts`），页面侧不做 unload 清理（unload 不可靠）。action API 失败一律吞掉只 warn（badge 属锦上添花，不能拖垮页面）。
- `use-daily-auto-sync.ts` — 每日首开自动同步协调器 hook（挂 `App.tsx`，跨路由常驻，单测 `use-daily-auto-sync.test.tsx`）。`useDailyAutoSync(platforms, deps?)` 的 `platforms` **必填**，由 `App.tsx` 注入 app 根 `collection-platform-auto-sync.ts` 的 `AUTO_SYNC_PLATFORMS`——hook 无默认 registry，本目录对 `sections/` 零 import（契约守卫，docs/20 高-3）。本文件拥有类型 `AutoSyncPolicy`（`probeReady` + 可选 `isSilentError`，各平台在 adapter 文件旁声明为 `<p>AutoSyncPolicy`）/ `AutoSyncDefinition`（+ `runSync`）/ `AutoSyncPlatform`（+ `itemPlatform`/`jobPlatform`，后者由 registry 经 `jobPlatformForCollection` 派生）。**触发 = mount + `visibilitychange`(visible)**（天然覆盖「登录后切回 tab 补拉」）；**节流 `EVALUATE_THROTTLE_MS=30_000`**（ref 记 `lastEvalAt`，用注入的 `deps.now()` 以便测试，防频繁切 tab 的 DB 查询风暴）。evaluate 每平台 `Promise.all` 并行 + try/catch 隔离（单平台失败/probe 抛错只 `console.error`，不阻断其它）：`shouldAutoSync(deps.getLastAttempt(itemPlatform))` 未命中或 `probeReady` false → 跳过；否则 `deps.startJob(jobPlatform,'sync', runner)` 派发（跨路由存活 + 并发去重 + indicator 可见），runner 只跑共享 Sync Adapter（`runSync`，尝试记录与处理派发经其内部的 funnel）+ `isSilentError` 命中的错不 rethrow——静默只是呈现，funnel 照样记 `'failure'`，所以静默同样占掉当天名额。`deps` 可注入（`initDb`/`now`/`getLastAttempt`/`isPaused`/`startJob`；`getLastAttempt` 默认读 `getPlatformSyncRecord(platform, await initDbProxy())?.lastAttemptAt`）。**闸门插桩在 `shouldAutoSync` 之后、`probeReady` 之前**（`deps.isPaused(jobPlatform)`，默认 `isLibraryPaused`）：暂停中不发探针请求、不记尝试，解除暂停后当天仍会补跑；这只是省掉噪音 job，真正的兜底是 `startJob` 的 born-paused（funnel 的首个 checkpoint 把尝试记录挡到恢复之后）。T3 组合测试用内存 record store 同时喂 funnel（写）与 `getLastAttempt`（读），`runSync` 调**真实** `runPlatformSync`，共用同一时钟。**StrictMode double-invoke 由闸门 + startJob 去重 + 节流天然幂等**。

## 约定

- **config 函数必须引用稳定**（模块级常量或 useCallback）——它们在 effect 依赖数组里，不稳定引用会每 render 重查。
- **泛型层零 storage / 零平台导入**：唯一依赖 `@/lib/database` 的 `initDbProxy`。auth/配置解析（如 X 的 `getXAuth()`）必须留在各平台的共享 Sync Adapter 模块（`sections/<platform>/<platform>-sync-adapter.ts`）内，hook 的 `syncFn` 只引用 adapter。**这条约束的是模块不是目录**：本目录分两档——泛型层（`background-jobs-store` / `pipeline-run-control` / `collection-processing-jobs` / `use-collection-library` / `facet-query` / `collection-phase` / `collection-sync-error` / `collection-sync-error-message` / `use-countdown` / `daily-sync-gate` / `pipeline-segments` / `use-processing-coverage` / `use-collection-pipeline`）与平台感知层（`library-gate` / `use-daily-auto-sync` / `platform-sync` / `use-credential-gated-library`，读 storage 或 DB、认识平台词汇是合法的）。跨档只能**由平台感知层向泛型层注入**（`setJobGate` / `deps`），泛型层反向 import 即视为掉档。**两档都不得 import `sections/`**：六平台 Sync Adapter 的聚合点在 app 根 `collection-platform-auto-sync.ts`，经 `App.tsx` 注入进 `useDailyAutoSync(platforms)`；契约测试扫描本目录全部非测试模块守卫。
- **平台同步语义单一实现**（audit #6 铁律）：「平台同步成功意味着什么」只在各 section 的 `*-sync-adapter.ts` 定义一次；手动 hook 与 app 根 daily registry（`collection-platform-auto-sync.ts`）都引用同一函数，禁止在任一触发方复制认证解析或后处理派发。**记录与派发只在 `platform-sync.ts` 的 funnel**（docs/32 Step 1）：adapter 在函数体内调 `runPlatformSync`，不自己调 `startCollectionProcessingJobs`、不自己写 Platform Sync Record（契约测试守卫前者）。触发策略留触发方：UI 门/冷却在页面 hook；daily 的 readiness/静默错误以 `<p>AutoSyncPolicy` 在 adapter 文件旁声明（不进 `run<P>Sync`），由 registry 配对。
- 消费方（薄 adapter，五个都以模块级 `JOB_PLATFORM = jobPlatformForCollection('<id>')` 作 `jobPlatform`、以模块级 `facetQuery(...)` 作 `queryFn`，docs/32 Step 5 / Step 7；各 ≤ 60 行，返回通用字段不改名）：`sections/github-stars/use-github-stars.ts` 与 `sections/youtube/use-youtube-playlists.ts`（都是 `return useCredentialGatedLibrary(<p>Credentials, config)`——凭据门统一成 `configured`，解析函数住在各自 adapter）、`sections/zhihu/use-zhihu-favorites.ts`（`return useCollectionLibrary(config)`）、`sections/x/use-x-bookmarks.ts`（`{ ...lib, lastInserted, cooldownRemainingMs }`：Platform Sync Record 的 `lastInserted` + 冷却，冷却锚点 = `lastSyncedAt`，倒计时走共享 `useCountdown`）、`sections/bookmarks/use-bookmarks.ts`（路由 folderId 经 `controlledFilter: folderId ?? null` 受控注入 + adapter 内 `useEffect` 挂载 `sync()`，docs/20 中-6；返回类型 `UseBookmarksReturn = Omit<UseCollectionLibraryReturn<…>, 'filter' | 'setFilter'>`——路由是 folder 的唯一事实源，view 看不到受控模式下是 no-op 的 `setFilter`）。**不适用**：bilibili（folders+videos 双 hook）——形态不同，不强行塞进该抽象（docs/15 HIGH-1 范围圈定），但其 sync runner 同样只调共享 Sync Adapter。
